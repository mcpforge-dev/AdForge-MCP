# Monthly Ads Report

Собирать отчёт только из трассируемых фактов. Не додумывать отсутствующие значения, события, причины и бизнес-результаты.

## Обязательные ресурсы

1. Читать [integration-contract.md](references/integration-contract.md) перед сопоставлением MCP-инструментов.
2. Читать [fact-policy.md](references/fact-policy.md) перед формированием вопросов, выводов и рекомендаций.
3. Читать [change-log.md](references/change-log.md) при проверке изменений.
4. Читать [questions.md](references/questions.md) при запросе недостающего контекста.
5. Читать [metrics.md](references/metrics.md) перед расчётами.
6. Читать [report-spec.md](references/report-spec.md) перед созданием результата.
7. Валидировать итоговый набор данных по [validated-report-data.schema.json](references/validated-report-data.schema.json) и скриптом `scripts/validate_report_input.py`.

## Рабочий процесс

### 1. Зафиксировать параметры

Получить отчётный месяц, часовой пояс, валюту, рекламные аккаунты, географию, модель атрибуции и каналы. Не смешивать данные с разными часовыми поясами, окнами атрибуции или валютами без явного преобразования.

### 2. Собрать данные

Вызвать доступные MCP-инструменты рекламных платформ. Сохранить исходный идентификатор аккаунта, кампании, группы, объявления, креатива и конверсии. Не полагаться только на изменяемые названия.

Для каждого значения записать статус происхождения:

- `SOURCE_FACT` — значение получено из системы-источника;
- `USER_CONFIRMED` — значение или причина подтверждены человеком;
- `CALCULATED` — значение рассчитано из перечисленных фактов по явной формуле;
- `UNKNOWN` — значение отсутствует или недоступно.

Не создавать статус для догадки. Предположение разрешать только как отдельно маркированную гипотезу, никогда как факт.

### 3. Проверить изменения

Сравнить отчётный период с предыдущим и журналом изменений. Проверять каждую кампанию, группу объявлений, объявление, креатив, конверсионное действие и бюджет.

Считать изменением как минимум:

- создание, запуск, паузу, возобновление, удаление или смену статуса;
- изменение бюджета, ставки, стратегии, цели, аудитории, географии, плейсмента, страницы или аккаунта;
- запуск или отключение креатива;
- изменение трекинга, атрибуции или конверсионных действий;
- заметное изменение объёма или эффективности согласно порогам интеграции.

Для каждого изменения искать запись по стабильному ID и периоду. Если причины нет, создать обязательный вопрос: `Что изменилось у <объект> <дата/период> и по какой причине?`

Не выводить причину из динамики метрик. Не подменять отсутствие записи фразами вроде «из-за обучения», «из-за сезонности» или «конкурент повысил ставки».

### 4. Найти недоступные факты

Сопоставить требуемые поля отчёта с реально подключёнными источниками. Для отсутствующих бизнес-данных сформировать вопросы. В первую очередь запросить качество лидов, этапы CRM, выручку, цены, решения клиента, блокировки, технические инциденты и причины ручных действий.

Задавать только релевантные вопросы. Группировать вопросы по теме и объекту. Не спрашивать то, что уже подтверждено источником или журналом.

### 5. Остановиться для уточнений

До получения ответов разрешать только `draft_with_gaps`: числовой черновик, список пробелов и список вопросов. Не формировать причинные выводы, ROI и финальные рекомендации на основе неизвестных данных.

Если пользователь отвечает «неизвестно» или отказывается отвечать, записать `UNKNOWN` с отметкой, кто и когда это подтвердил. Не задавать тот же вопрос повторно в текущем цикле.

### 6. Рассчитать показатели

Рассчитывать только показатели с полным набором операндов. Записывать формулу и `evidence_ids`. Не делить на ноль. Не суммировать несовместимые конверсии и не называть платформенную конверсию лидом без утверждённого определения.

### 7. Сформировать утверждения

Для каждого содержательного утверждения перечислить подтверждающие `fact_ids` или `change_ids`.

- Описывать факт напрямую, если доказательство полное.
- Маркировать расчёт как расчёт.
- Формулировать гипотезу только с явной пометкой «гипотеза» и вопросом для проверки.
- Удалять утверждение, если оно требует неизвестной причины.
- Не раскрывать стратегию, бюджет или ставки конкурента по Auction Insights: эти данные показывают результат аукциона, а не внутренние настройки конкурента.

### 8. Провести контрольный шлюз

Запустить:

```bash
python scripts/validate_report_input.py validated-report-data.json
```

Не выпускать финальный аналитический отчёт при ошибках. Предупреждения `UNKNOWN` допускать только при явном отображении пробела в отчёте и запрете зависимых выводов.

### 9. Подготовить отчёт

Следовать [report-spec.md](references/report-spec.md). При создании PPTX использовать `assets/monthly-report-template.pptx` как визуальный и структурный источник, сохранять исходник и экспортировать новую копию. Не переносить из шаблона старые цифры или выводы.

Включать приложение или машинно-читаемый реестр источников: показатель/утверждение → статус → источник → дата получения.

## Финальный ответ пользователю

Сообщить:

- какие источники использованы;
- какие вопросы были подтверждены;
- какие данные остались `UNKNOWN`;
- какие разделы или выводы из-за этого ограничены;
- где сохранён отчёт и файл валидации.
