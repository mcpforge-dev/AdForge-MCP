## 1. Карточки проблем по экранам

### 1.1 Landing (`#landing`)
- Hero-заголовок и структура хорошие, но 3 uppercase-eyebrow («AI-ПОМОЩНИК…», «AI-АНАЛИЗ САЙТА», «ПОСЛЕ ПОДКЛЮЧЕНИЯ») — узнаваемый AI-шаблон.
- Под hero 4 чипа-бенефита + схема из 3 flow-карточек со стрелками «→» — карточки-клише; на mobile схема растягивается на 476px высоты и дублирует текст hero.
- `feature-grid` — три одинаковые карточки (классический «3 equal cards»); первая («Подключение через сайт») дублирует чип из hero.
- Нет ни одного скриншота продукта / визуального доказательства — только текст и плашки. Для продукта с dashboard'ом это упущение доверия.
- Нет секции социального доказательства (кому уже помог), нет FAQ/возражений («это безопасно?» закрыто одним чипом).
- CTA-дубли: «Зарегистрироваться» (hero) и «Регистрация» (шапка) — одна интенция, два разных лейбла.
- Провал контраста primary-кнопок (3.43:1) — прямо на «Зарегистрироваться».

### 1.2 Header и навигация (site-header / topbar / tabs-bar)
- Лендинговая шапка минимальна — нормально; активное состояние раздела в кабинете есть (`is-active`), но вкладка 35px высотой, а на mobile полоса вкладок скроллится без градиента/стрелки-подсказки.
- Постоянный бейдж «Безопасный режим: без автозапуска» рядом с вкладками — полезный смысл, но как вечная плашка = шум; читается как предупреждение об ошибке.
- Логотип — градиентная точка (`--accent → #9f7cff`): единственный градиент; либо осознанно оставить как знак, либо упростить (решение бренда, менять без согласования нельзя).

### 1.3 Вход (login)
- Модалка с табами «Вход/Регистрация», Google-кнопка, «Забыли пароль?» — структура здравая.
- «Показать» у пароля — текстовая кнопка без минимальной ширины: при переключении «Показать/Скрыть» дёргается ширина.
- Ошибка (`gate__error`) выводится одним блоком под формой, а не у конкретного поля.
- Фокус-стили инпутов: `outline: none` + смена цвета border — слабый индикатор для клавиатуры.

### 1.4 Регистрация
- Поле «Код регистрации (если выдан)» с подсказкой «Код от менеджера HolyMedia» — хорошо объяснено; но `<small>` внутри лейбла мелкий и faint (провал контраста).
- Подтверждение пароля есть; требований к паролю кроме placeholder «Минимум 8 символов» не видно — при ошибке валидации пользователь узнаёт постфактум.
- Экран успеха («Аккаунт создан», ✓) — хороший момент; галочка стилизована бедно относительно важности момента.

### 1.5 Forgot / Reset password
- Тексты хорошие и человеческие («Мы не показываем, существует аккаунт с такой почтой или нет»).
- Формы генерируются в универсальную `client-modal` — визуально беднее auth-модалки, нет иконки/акцента состояния.
- После reset — авто-переход на login через 900ms: быстро, пользователь может не успеть прочитать «Пароль изменён».

### 1.6 Welcome pop-up
- Два сценария (register/return) — правильно; но контент — «welcome-card» (карточка в модалке) с одним абзацем: вложенная плашка ради плашки.
- Не показывает прогресс (0 из 3 шагов) — упущенная связка с чек-листом «Начала работы».

### 1.7 Onboarding / «Начало работы»
- 6 stat-плиток («Сервис: Работает», «Адрес кабинета» моноширинным, «Режим работы: Без автозапуска»…) — половина не несёт действия и дублирует бейдж; классический hero-metric шум.
- Чек-лист из 3 шагов — правильная идея; но шаг «Скопируйте MCP URL» отмечается только если пользователь нажал кнопку копирования в этой сессии (state в памяти) — прогресс «прыгает» после перезагрузки.
- Блок «Дальше в AI-клиенте» — курсивная вставка с кавычками-ёлочками и “смешанными” кавычками в одном экране.
- Две карточки грид-2 с почти одинаковым весом — непонятно, что главное действие.

### 1.8 Connections («Подключения»)
- Карточка платформы перегружена: заголовок + описание + бейдж статуса + meta-строка + hint + callout + аккаунты + 1-2 кнопки. До 4 плашек разных тонов в одной карточке.
- Статусная система богатая (connected/select_accounts/reconnect_required/provider_setup_required/credentials_missing/ready_to_connect) — это сильная сторона; но каждый статус = цветной бейдж, и глаз не отличает важное от фонового.
- «Отключить» — danger-кнопка без подтверждения (проверить: похоже, disconnect выполняется сразу).
- Пустое состояние: «Пока нет подключенных рекламных аккаунтов. Начните с подключения…» — текст без действия (кнопки подключения — ниже в карточках, но пустое состояние само не ведёт).

### 1.9 Pop-up выбора рекламных аккаунтов (pending)
- Функционально насыщенный (select all, счётчик, диагностика pending, ручной ввод Google customer id) — сохранить логику.
- Диагностика внутри попапа (`pending-diagnostics`) — техническая сетка ключ-значение, в клиентском сценарии выглядит как отладка.
- Попап открывается автоматически при наличии pending — правильно, dismissed-логика есть.

### 1.10 MCP («Подключение к AI-клиенту»)
- Лучший по смыслу раздел (шаги 1-4), худший по форме: карточка → внутри setup-card → внутри client-grid из карточек-табов → внутри ai-client-panel (ещё карточка). 3 уровня вложенных карточек.
- 3 карточки клиентов с одинаковым бейджем «Готово» — бейджи не различают ничего.
- «Скопировать значение для Authorization» — самая техническая кнопка в клиентском UI.
- Поля для Claude: «OAuth Client ID / Client Secret / оставьте пустым» — необходимая сложность, но подана как таблица кодов без объяснения, «что это вообще».
- Секция дублирует блок «Подключение к AI-клиенту» с Overview (2 места с mcp-url) — допустимо, но нужно визуальное различие ролей.
- Ключ «будет показан только один раз» — критический момент без визуального веса (тот же callout, что и всё остальное).

### 1.11 Инструкции Codex / Claude / ChatGPT
- Пошаговые списки хорошие и конкретные.
- Смешение регистров: «Settings / Настройки», «Add server», `Authorization`, `Bearer <ваш ключ доступа>` — неизбежный минимум, но не отделён визуально от человеческого текста (всё в одном потоке).
- Табы-карточки клиентов не выглядят как табы (выглядят как ещё три карточки контента).

### 1.12 SEO
- Отчёт информативный: метрики + дельты, executive summary, инсайты, тренд, таблицы, opportunities, sitemap.
- «SEO score» — крупная цветная плашка с внутренней эвристикой (55 + бонусы): выглядит авторитетно, но это самодельный индекс; для клиентского отчёта рискованно без пояснения.
- Плотность: до 9 блоков подряд одинаковой карточной вёрстки, нет визуальной иерархии «сначала вывод → потом данные».
- Таблицы `min-width: 560px` со скроллом на mobile — приемлемо, но без sticky-заголовка и без подсказки о скролле.
- Тон дельт: «+12% к прошлому периоду» окрашивается ok/warn — хорошо; «нет сравнения» — muted чип, снова чип.
- Экспорт: «Скачать отчет» отдаёт **RTF** (Arial, `\bullet` строки, таблицы «текст с | разделителями») — по качеству это не клиентский документ агентства.

### 1.13 AI-анализ сайта (форма)
- 8 полей формы сразу (URL, тип, цель, режим, аудитория, регион, конкурент, боль) — для «быстрого анализа» это стена; только URL обязателен, но визуально все равны.
- Хорошо: честные подсказки «Показываем источники и границы выводов», «Security-блок пассивный…» — но написаны мелким faint-текстом (контраст-провал) и с техническими словами («viewport», «rendered DOM», «Pillow»).
- Кнопка «Проанализировать сайт» — btn--block на всю ширину сетки: конкурирует с самим отчётом ниже.

### 1.14 Результаты анализа
- Самый насыщенный экран продукта: score-карточка, вердикт, KPI-чипы, допущения, 9 табов, score-карты с прогресс-барами, топ улучшений, скриншоты, «1 день», готовые тексты…
- 9 табов во второй строке навигации («Топ улучшений», «Диагностика», «Первый экран», «1 день», «Что поправить», «Готовые тексты», «Структура», «План внедрения», «Вопросы») — превышение рабочей памяти (≤4-5); часть названий пересекается по смыслу («Топ улучшений» vs «Что поправить» vs «План внедрения»).
- 5 кнопок действий подряд (Скачать / Скопировать отчёт / Задачи команде / Hero-тексты / Новый анализ) — все secondary-ряд, кроме первой.
- KPI-чипы: «Ниша: auto», «CTA найден», «Достоверность: 78%» — россыпь разноцветных чипов.
- Score-бары с заливкой + цветовое кодирование is-risk/is-watch/is-strong — тот самый «яркий score-бейдж» стиль.
- Заголовок «Hero-тексты» на кнопке — жаргон (клиент не знает слова hero).

### 1.15 Профиль
- Смена никнейма/фото/пароля; аватар 64px на mobile; аватар-кнопка имеет focus-within — точечно хорошо.
- Раздел визуально беднее остальных (одна карточка) — несоответствие уровня отделки.

### 1.16 Аватар
- Загрузка через кнопку-аватар; превью есть. Нет подсказки о требованиях к файлу (размер/формат) до выбора; ошибки — через toast.

### 1.17 Смена пароля
- Отдельная модалка; та же слабость фокус-стилей и ошибок «одним блоком».

### 1.18 Toast / modal / loading / error states
- Toast: 1 стиль, 4 тона — ок; `aria-live` есть — хорошо.
- Loading: везде «Загружаем…» текст в empty-state или спиннер в модалке отчёта («Подождите, отчёт собирается») — нет skeleton'ов; интерфейс «мигает» пустыми блоками.
- Error: `errorState()` — красный текст в блоке; `humanizeError` переводит ошибки на русский — сильная сторона; но стилистика ошибок и предупреждений совпадает с остальными callout'ами.
- `window.confirm` в admin (отзыв MCP token) — системный диалог ломает стиль и не стилизуется.
- Модалки: закрытие по backdrop и ×; Esc — проверить; focus-trap отсутствует (доступность).

### 1.19 Скачиваемые отчёты
- **AI-аудит (HTML-документ)**: светлая тема, Arial, зелёная плашка score, синие таблицы — выглядит как generic-отчёт, не как документ HolyMedia (нет логотипа, фирменного знака, типографики бренда). Русский текст + `—` — нормально для RU-типографики.
- **SEO (RTF)**: заголовки жирным, «таблицы» через « | » — непригодно как клиентский документ агентства; CSV — ок как данные.
- Ни в одном документе нет: обложки с брендом, оглавления, колонтитулов, контактов агентства, версии/автора.

### 1.20 Admin
- Таблица пользователей 8 колонок `min-width: 760px` — терпимо для admin.
- Английские лейблы вперемешку с русскими («Database», «Driver», «Active sessions», «Overall», «Env credentials», «Last attempt») — для admin допустимо, но дешевит.
- `window.confirm` для отзыва токена.
- Наследует все токены — после смены токенов должен «поехать» бесплатно; отдельного редизайна не требует (решение подтверждено).

### 1.21 Desktop / tablet / mobile
- Desktop: shell 1280px, ок.
- Tablet: breakpoint 860px переводит почти всё в 1 колонку — между 860 и 1280 сетки местами растянуты (2 колонки с большими пустотами).
- Mobile: без горизонтального overflow (проверено), но тач-цели 31-39px, полоса вкладок со скрытым скроллом, таблицы со скроллом без подсказки.
- Диагностика: секция `#section-diagnostics` есть в DOM, но **вкладки для неё нет** в tabs-bar — мёртвый вес/сирота в IA (доступна только если код где-то вызывает setSection, который для неизвестной секции откатывается на overview).

## 2. Повторяющиеся анти-паттерны (сквозные)

1. **Бейдж/чип-перенасыщение** — 5 тонов бейджей + чипы + KPI-чипы + статус-плашки; в одной карточке платформы до 4 плашек. Всё выделено → ничего не выделено.
2. **Карточка как единица вёрстки + вложенные карточки** — `setup-card` в `mcp-card`, `welcome-card` в модалке, `cardlet` в блоках анализа, `admin-oauth-card` в card. До 3 уровней рамок.
3. **Ряды равнозначных кнопок** — 5 кнопок у результата анализа, 5 в MCP, 3 в SEO-шапке; primary теряется.
4. **Технотермины в клиентском UI** — MCP URL, token, OAuth Client ID/Secret, transport, read-only, viewport, rendered DOM, Pillow, evidence, Authorization, Bearer.
5. **Яркие score-элементы** — SEO score плашка, score-бары с заливкой, цветовые классы is-risk/is-watch/is-strong, зелёная плашка в HTML-отчёте.
6. **«Загружаем…» вместо skeleton** — везде текстовые заглушки или спиннер; контент «прыгает».
7. **Слабые фокус-стили и нулевой reduced-motion** — `outline: none` у полей, focus-visible у 2 элементов, 0 `prefers-reduced-motion`.
8. **Uppercase-tracked eyebrows** на лендинге и в отчётах (`site-analysis-eyebrow`, `seo-eyebrow`) — AI-шаблон.
9. **Тач-цели ниже 44px** — вкладки 35px, малые кнопки 31px.
10. **Пустые состояния-констатации** — «Пользователей пока нет.», «Данных нет.» — не учат следующему шагу.
11. **Системные confirm/alert** — ломают стиль, не переводятся.
12. **Смешение языков/регистров** — «Hero-тексты», «CTA найден», англ. лейблы в admin, «Settings / Настройки».

Что **не** подтвердилось (сильные стороны, сохранить): кислотных градиентов нет (один мягкий на лого-точке); палитра дисциплинированная (нейтрали + 1 акцент); `humanizeError` и многие тексты уже человеческие; статусная модель подключений продумана; экранирование `esc/escAttr` последовательное; преview-безопасность как ценность прошита в тексты.

## 3. Аудит текстов

### Удалить
- Бейджи «Готово» ×3 на карточках AI-клиентов (не несут информации).
- Stat-плитки «Сервис: Работает», «Режим работы: Без автозапуска», «Адрес кабинета» (дублируют бейдж и URL-блок).
- Дублирующий чип «Подключение через сайт» в hero (есть одноимённая фича-карточка).
- «Pillow-анализ недоступен» — внутренняя деталь реализации.
- Постоянный бейдж «Безопасный режим…» в текущем виде (перенести смысл в спокойную строку под шапкой или в welcome/первый экран).

### Сократить
- Подзаголовки секций кабинета (везде 1,5-2 строки: «Скопируйте адрес подключения, создайте личный ключ и выберите инструкцию…» → «Подключите HolyMedia MCP к вашему AI-клиенту за 4 шага»).

### Таблицы (SEO, admin)
- Заголовок sticky, tabular-nums, выравнивание чисел вправо, зебра нет — разделители `border-bottom` только между строками, hover-подсветка строки.

- Карточка = граница реальной сущности (платформа, отчёт в истории). Разделы и шаги — заголовок + отступы, без рамки.

### Pop-up / модалки
- Единый компонент: заголовок, подзаголовок, тело, «полка» действий (primary справа), × и Esc, focus-trap, `aria-modal`.
- Заменить `window.confirm` на стилизованный confirm-диалог.
- Welcome — 1 экран с 3 шагами прогресса и одной primary-кнопкой.

### Состояния

- Motion: 150-250ms ease-out, только состояние (tab switch, toast, dropdown); всё под `prefers-reduced-motion: reduce`.

## 8. Риски для функциональности

1. **JS завязан на классы и структуру DOM**: `app.js` рендерит HTML-строками и ищет `.is-active`, `data-nav`, `data-site-tab`, id-элементы (`cache()` на ~150 id). Переименование классов/id без синхронного апдейта JS ломает разделы. Митигация: сохранять все `id` и `data-*`; менять только CSS-классы презентации, JS-шаблоны править точечно.
2. **Экранирование**: любые изменения шаблонов обязаны сохранять `esc()/escAttr()` — риск XSS при небрежной правке.
3. **State-логика онбординга** (`mcpUrlCopied`, dismissed pending в localStorage) — при перестройке блоков не потерять привязку кнопок копирования (`markMcpUrlCopied`).
4. **OAuth-потоки**: кнопки `data-oauth`, `data-pending`, redirect-обработка `pendingOAuthAuthorizeTarget()` — попап выбора аккаунтов критичен для онбординга; менять только оболочку.
5. **Показ ключа один раз**: `mcp-token-reveal` — UX-критичный блок; ошибка в рендере = пользователь теряет ключ.
6. **Экспорт отчётов**: `siteAnalysisDocumentHtml`/`seoRtf` генерируются в JS; замена RTF на HTML меняет расширение файла — предупредить пользователей беты.
7. **Статика захардкожена в server.py** (`/assets/app.css`, `/assets/app.js` пофайлово): для шрифтов/новых ассетов нужен новый маршрут — это правка Python, покрыть тестом.
8. **Тесты**: есть pytest и `node --check`; UI-тестов нет — регрессии ловятся только глазами. Перед этапом 3 зафиксировать чек-лист ручной проверки по разделам.
9. **Кэширование**: `app.css?`/`app.js` без версии в query (favicon имеет `?v=3`) — у беты может закэшироваться старый CSS; добавить версионирование при деплое.
10. **Playwright-скриншоты в проде** (site analysis) — не трогаем; наша работа только над статикой.
